# QuickVault 1.0.0

The first release: an offline-first, end-to-end encrypted password manager
for Linux, Windows and Android, with direct sync between devices on the same
local network. There is no server and no account. AGPL-3.0-or-later.

This file is the release record that 0012 §3 asks for. It says what was
checked, and states plainly what was not.

## What is in it

- The desktop and phone app (`quickvault`) and the command-line client
  (`qv`), with one shared vault format.
- Vaults: logins, cards, Wi-Fi, notes and custom items; groups; attachments
  up to 2 GiB with previews; history; trash; snapshots kept inside the
  vault; archives for backup and exchange.
- Sync: one scan of a QR code (or a typed code) syncs two devices on the
  same network, with conflicts shown for the user to resolve.
- Android: fingerprint unlock (keystore-bound) and autofill.

The published Alpine package requires libxdo.so.3 and is incompatible with
current Edge repositories, which provide libxdo.so.4. Subsequent release
builds provide separate `alpine-3.22` and `alpine-edge` assets (plan 0066).

**Signing** (owner decision, 0012 §3): the artifacts are not signed. The
Android APK is signed with one stable project key so that later releases
install over it; that key shows continuity, not identity. The Alpine package
carries a signature from a throwaway key, so it needs `--allow-untrusted`.

**Reproducible builds:** not verified. The Linux tarball script uses fixed
archive metadata, but nobody has checked that two builds of the binaries
match byte for byte.

## Formats

The vault, archive and snapshot formats are frozen as of this release
(spec 0015). Every later version must open 1.0 files. The golden files in
`crates/qv-store/tests/golden/` and `crates/qv-model/tests/golden/` enforce
this. Vaults made by development builds open unchanged.

## Security status: what was not done

1.0 has **not** had an independent security audit. In particular:

- **LAN protocol review (D12):** a separate agent source/composition review
  is completed in [plan 0065](../../plans/0065-release-review-repairs/LAN-REVIEW.md).
  It found and repaired an initiator deadline gap and quadratic progress
  accounting. The same reviewer wrote those repairs. This satisfies the
  owner's request for another agent session, and is not an independent-party
  audit or proof of security. Independent composition/dependency assessment,
  complete error-transition vectors and attended LAN evidence remain open.
- **Dependency audits:** `cargo vet` passes on recorded exemptions, and an
  exemption is not an audit. Several security-critical crates have no audit
  that matches the pinned version and configuration:
  - the OPAQUE family (`opaque-ke` 4.0.1; NCC reviewed 0.5.0 in 2021);
  - `libcrux-kem` 0.0.10 (X-Wing);
  - the `rusqlite` 0.41.0 / bundled SQLite 3.54.1 delta;
  - the RustCrypto AEAD, hash, HKDF and Argon2 crates at the pinned
    versions.

  Details are in `plans/0048-security-release-validation/DEPENDENCY-REVIEW.md`.
- **Code reviews:** the security-critical plans not reviewed before had
  fresh-context reviews for 1.0 (0049, 0050, 0059, 0060, 0063, 0064); their
  findings are repaired in plan 0065, including the remaining compaction,
  import-stream, recovery-copy, quick-unlock and golden-coverage issues.
  Older actionable biometric, Wayland and clipboard-exclusion findings also
  have source repairs; the published memory/OS-copy limits remain.
  Target/device qualification remains open under *Known limitations*. By owner decision, the UI and app plans (0040–0045, 0051, 0054,
  0057, 0058, 0061, 0062) and the rest of the Windows plan 0052 ship without
  a fresh-context review (0045's quick-unlock policy and 0052's clipboard
  code had partial reviews). `plans/README.md` lists each plan's status.
- **Password hashing:** password-kdf/1 is Argon2id with 256 MiB, t=3, p=4.
  It was benchmarked on the development host (unlock about 0.5 s including
  the derivation), not measured on a phone. It is in daily use on the
  owner's Android test phone (0002 §1.3).

## Known limitations

- **Memory:** the app's own secrets live in zeroized containers, but the
  web view, the UI framework and the OS make copies that QuickVault cannot
  wipe (0008 §1.1, §4.4). Standard Unicode lowercasing can also leave
  unwiped intermediate allocations (0008 §6). A memory dump of a running, unlocked app can
  expose secrets.
- **Clipboard:** copies clear after 20 seconds. Clipboard managers and
  history (Windows clipboard history, X11 and Wayland managers, Android
  keyboards) may keep copies outside QuickVault's control. Windows may
  retain system copies and free a replaced clipboard block without an
  application wipe; exclusion hints are published before plaintext.
- **Devices that were not validated:** there are no attended records for:
  - the 0039 two-device LAN interruption checks;
  - the 0049 picker and 0050 media checks under an isolated UID;
  - a phone performance run;
  - the attended Windows checklist (`plans/0052-windows-platform/WINDOWS-GATES.md`).

  The owner's informal phone and desktop use, including LAN sync between
  them, was the only device testing.
- **Platforms:** no macOS, iOS, browser extension or BSD build. No remote
  server: sync works only between devices on the same network.
- **Local availability:** idle unauthenticated connections cannot hold all
  pending webview slots, but sustained local connection flooding can still
  delay the app's bounded loopback listener.
- **Qualification:** the 8 GiB near-budget import test is corrected for the
  raised limits but has not been rerun at that size; the earlier 1 GiB figures
  are historical. Windows cross-compilation and Wine runs are development
  evidence, not actual Windows release qualification. Compaction requires
  POSIX replacement support from the Windows filesystem; unsupported
  replacement fails while preserving the original vault and its lock.
- **Linux audio previews** play without live level bars, because of a
  WebKitGTK routing fault (`crates/qv-app/WEBKIT.md`).
